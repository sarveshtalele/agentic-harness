# Skill Studio audit

Audited on 2026-11-10 against `src/backend/api/skills.py` (674 lines) and `src/frontend/app/skills/studio/page.tsx` (1254 lines). Each issue is closed by the M3 rebuild (`docs/MASTER_PLAN.md`) and by a test named in the last column.

## Security

| # | Issue | Where | Fix | Test |
|---|---|---|---|---|
| S1 | Any signed-in user, a viewer included, can create, overwrite and delete skills and run skill scripts. All `/api/skills/*` routes are only "signed in" (`core/auth.py` SESSION_ONLY) | `api/skills.py` | Writes and script runs need the admin role or a `skill_author` grant. Viewers read only | `test_skill_studio_permissions` |
| S2 | `execute-script` runs any skill's Python with `cwd` set to the platform root, on the API host, in every profile | `api/skills.py` `execute_skill_script` | Runs in a temporary copy of the skill folder with `clean_env()` and a timeout. Allowed only in the `local` and `desktop` profiles; `web` answers 403 | `test_script_runs_only_in_a_scratch_copy` |
| S3 | `list_studio_documents` returns documents from every project, including ones the user cannot see | `api/skills.py` | Filter by `auth.can_see_project` | `test_studio_documents_are_permission_filtered` |
| S4 | `save` writes any `SKILL.md` and `run.py` sent by the browser, with no validation, and overwrites an existing skill, core skills included | `api/skills.py` `save_skill` | Validation runs before writing: frontmatter, name rules, scanner. Core skills are read-only. Every save is a new immutable version | `test_save_validates_and_versions` |
| S5 | `delete` removes any non-core folder at once, with no version kept | `api/skills.py` `delete_skill` | Admin only. The folder goes, but its versions stay in the database and the ledger records the deletion | `test_delete_keeps_versions` |

## Fabricated or misleading output

| # | Issue | Where | Fix | Test |
|---|---|---|---|---|
| F1 | When no tasks are sent, scaffold invents five generic steps ("Ingest input parameters...") | `scaffold_skill` | No tasks means no generation; the approved plan is required | `test_generate_requires_an_approved_plan` |
| F2 | The SKILL.md is a fixed template ("Capabilities & Scope... enterprise verification rules"); the model writes nothing in it | `scaffold_skill` | The model writes each file from the approved plan and the source document | `test_generated_skill_body_comes_from_the_model` (scripted model) and a live story |
| F3 | Metadata is invented: `version: "1.4.0"`, author "Agentic QE Engineer", and a description suffix "Grounded in project specifications" | `scaffold_skill` | Version 1 for a new skill, the signed-in author, and the model's description as approved | same |
| F4 | `evals.json` cases are "Verify task execution: <task>", with no input and no checkable expectation | `scaffold_skill` | Eval cases carry a real input from the source and deterministic assertions (contains, regex, JSON keys) | `test_eval_cases_have_inputs_and_assertions` |
| F5 | Test cases are generated by index: case 4 is always "Negative", case 5 always "Exception", and the oracle is always "exit code 0" | `scaffold_skill` | Removed. The QE workflow designs test cases; the Studio no longer pretends to | covered by F4 |
| F6 | "Attach to QE" writes those generated cases into a project document marked `- [x]` "Verified Skill Tasks", although nothing was verified | `attach_to_qe_workflow` | Removed with F5. A skill is offered to the QE workflow as a skill, not as invented test cases | `test_attach_route_is_gone` |
| F7 | The suggest prompt forces "Autonomous skill for..." wording and exactly 5 tasks of a fixed shape (AST parsing, invariant verification, audit trace) whatever the request | `_run_skill_creator_llm` | The prompt follows Agent Skills best practice: a third-person description with "Use when", as many tasks as the work needs, and no forced shape | `test_plan_prompt_has_no_forced_shape` |
| F8 | The model call bypasses MAF (raw `httpx` to `/chat/completions`), with no tool audit, no token count and no prompt version | `_run_skill_creator_llm` | Calls go through `runtime.AgentCall` with the `skill-creator` agent policy and a versioned prompt (`prompts/skill-creator.md`) | `test_plan_call_is_recorded_in_agent_calls` |

## Missing features the owner asked for

| # | Missing | Fix |
|---|---|---|
| M1 | No choice between an **instructions-only** skill and a **script-based** skill. A checkbox `includeScript` defaults to on | First step: choose the kind. It changes the plan, the files and the tests |
| M2 | No **sub-agent plan** (which specialist handles which part) and no **output formatting** plan | The plan has `subagents` (each with name, role and when to use) and `formats` (each with a name and a template in `assets/`) |
| M3 | Task-list approval exists only in the browser; the server generates from anything | The server stores the approved plan with its SHA-256 and generates only from that hash |
| M4 | Skills are not really tested. A script that exits 2 is the whole "execution" | A script skill must ship `scripts/test_*.py`, which run in the sandbox. Any skill can run on a real sample from the project's documents |
| M5 | Evaluation does not use the model | Eval cases run on the real model with and without the skill. Scores are stored in `evaluation_metrics` with judge, `n` and source |
| M6 | No versions; a re-save overwrites | `skill_versions` table, plus a ledger entry per version |
| M7 | No zip upload or download | Zip upload with a zip-slip guard and the same checks; zip download per version |
| M8 | The page is one 1254-line file | `features/skills-studio/` with one component per step |
